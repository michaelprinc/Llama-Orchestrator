# Llama-Orchestrator GUI `app.py` Refactoring Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Divide the 3,845-line `gui/app.py` into 19 independently-refactorable modules using script-based section analysis, reducing context fill per refactoring task from ~3,800 lines to ~50-400 lines.

**Architecture:** Script-first analysis → section extraction → independent module refactoring → unified `__init__.py` re-export. Each section is extracted as a standalone module with its own imports, then the main `app.py` is reduced to a thin coordinator that imports from the extracted modules.

**Tech Stack:** Python 3.13, Tkinter, dataclasses, threading, pathlib

## Refactoring Strategy

### Phase 0: Preparation (order 1)
1. **Backup** `app.py` → `app.py.bak`
2. **Create** the analysis script (already done: `.hermes/scripts/analyze_app_sections.py`)
3. **Verify** existing tests pass against current `app.py`

### Phase 1: Independent Module Extraction (order 2–4)
Extract modules with **no or minimal dependencies** first. These are self-contained and can be verified independently.

- **Order 1:** `dataclasses.py` (31 lines, no deps)
- **Order 2:** `grid_dialogs.py` (100 lines, deps: dataclasses)
- **Order 3:** `kv_cache_dialogs.py` (119 lines, deps: grid_dialogs)
- **Order 4:** `model_dialogs.py` (309 lines, deps: dataclasses)
- **Order 5:** `hf_import_dialog.py` (459 lines, deps: dataclasses)
- **Order 6:** `install_dialog.py` (72 lines, no deps)

### Phase 2: Main GUI Class Extraction (order 5–16)
Extract `LlamaOrchestratorGui` methods into separate modules in dependency order. Each module becomes a **partial class** that is later mixed into the main class.

- **Order 5:** `gui_widgets.py` (344 lines) — foundation, all other GUI modules depend on this
- **Order 6:** `gui_messages.py` (25 lines)
- **Order 7:** `gui_refresh.py` (269 lines)
- **Order 8:** `gui_selection.py` (52 lines)
- **Order 9:** `gui_instances.py` (39 lines)
- **Order 10:** `gui_benchmark.py` (357 lines)
- **Order 11:** `gui_benchmark_settings.py` (197 lines)
- **Order 12:** `gui_prompts.py` (69 lines)
- **Order 13:** `gui_actions.py` (153 lines)
- **Order 14:** `gui_daemon.py` (141 lines)
- **Order 15:** `gui_files.py` (40 lines)
- **Order 16:** `gui_dialogs.py` (103 lines)

### Phase 3: Assembly (order 17)
1. Create the **coordinator** `app.py` that imports all extracted modules
2. Mix in partial classes into `LlamaOrchestratorGui`
3. Update `__init__.py` to re-export from the new module structure

### Phase 4: Cleanup (order 18)
1. Remove duplicate code from old `gui/dialogs.py` (already extracted)
2. Update `gui/refresh.py` if needed (already has RefreshController)
3. Remove `gui.py` fallback (or keep for backward compat)
4. Final test run

## Risks & Tradeoffs

| Risk | Mitigation |
|------|-----------|
| Circular imports between GUI modules | Keep dependency graph acyclic; use TYPE_CHECKING imports where needed |
| `__init__.py` re-export breaking existing code | Preserve all existing import paths; test against `tests/test_gui.py` |
| Dynamic fallback in `__init__.py` | Keep the `exec(compile(...))` fallback for `gui.py` as safety net |
| Large method boundaries (e.g., `_export_config_to_vscode` at 140 lines) | Extract as-is; refactor method internals in a follow-up |
| Cross-module state sharing (e.g., `_row_map`, `_benchmark_active_name`) | Keep shared state in the coordinator `app.py`; pass via method parameters |
